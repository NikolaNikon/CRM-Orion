# Orion: рабочий процесс и синхронизация с Twenty

## Цель

Orion построен на базе Twenty. Работа с проектом должна разделять две независимые категории изменений: собственные доработки Orion и регулярное получение улучшений из `twentyhq/twenty`. Это позволяет сохранять контролируемую историю проекта, проще проверять обновления и безопасно откатывать проблемные изменения.

## Ежедневная работа

Начинайте новую задачу от актуальной `main` и создавайте отдельную тематическую ветку. Используйте префикс `feat/` для функциональности, `fix/` для исправлений и `chore/` для технических работ.

```bash
git checkout main
git pull --ff-only origin main
git checkout -b feat/<краткое-название>
```

После внесения изменений запускайте только относящиеся к задаче проверки, а затем открывайте Pull Request в `main`. Не делайте прямых коммитов в `main`; Pull Request обеспечивает проверяемую историю, CI и безопасный rollback.

| Тип работы | Пример ветки | Ожидаемый результат |
|---|---|---|
| Новая бизнес-функция | `feat/company-import` | Pull Request с описанием сценария, миграциями и проверками. |
| Исправление | `fix/contact-filter` | Pull Request с воспроизведением проблемы и регрессионной проверкой. |
| Технический долг | `chore/update-observability` | Изолированный Pull Request без смешивания с продуктовой функцией. |
| Обновление upstream | `chore/sync-twenty-upstream` | Отдельный автоматически поддерживаемый Pull Request. |

## Локальный запуск

Для установки зависимостей и запуска проекта необходимы Node.js 24.5+ и Yarn 4. Команды запуска зависят от выбранного компонента, но базовая последовательность выглядит так:

```bash
corepack enable
yarn install --immutable
yarn start
```

Полный local stack требует PostgreSQL и Redis. Для контейнерного варианта используйте конфигурацию в `packages/twenty-docker`; перед подключением к реальным внешним сервисам заполните отдельный `.env` и не добавляйте секреты в Git.

## Еженедельная синхронизация с Twenty

Workflow `.github/workflows/orion-upstream-sync.yaml` запускается каждый понедельник в 06:00 UTC (09:00 UTC+3) и также доступен для ручного запуска на странице Actions. Он выполняет следующий процесс:

1. Загружает актуальную ветку `main` из `twentyhq/twenty`.
2. Проверяет, есть ли новые коммиты относительно Orion.
3. Если обновление требуется, сливает upstream в ветку `chore/sync-twenty-upstream`.
4. Создаёт новый либо обновляет существующий Pull Request в `main`.
5. Никогда не выполняет автоматический merge в `main`.

Если merge вызывает конфликт, workflow завершается ошибкой без изменений в `main`. Конфликт нужно решить в ветке синхронизации, после чего можно продолжить обычную проверку Pull Request.

### Однократная настройка секрета

Для того чтобы Pull Request запускал обычный CI, workflow использует отдельный fine-grained GitHub Personal Access Token. Создайте токен в GitHub для репозитория `NikolaNikon/CRM-Orion` с правами `Contents: Read and write`, `Pull requests: Read and write` и `Metadata: Read`, затем сохраните его в настройках репозитория как Actions secret с точным именем:

```text
ORION_UPSTREAM_SYNC_TOKEN
```

После добавления секрета откройте **Actions → Orion weekly upstream sync → Run workflow** и выполните один ручной запуск. Это проверит токен и убедится, что процесс способен создавать Pull Request.

## Проверка Pull Request синхронизации

Перед слиянием еженедельного PR:

1. Проверьте статус CI и сначала устраните все красные проверки.
2. Просмотрите изменения в миграциях, зависимостях, Docker-конфигурации и переменных окружения.
3. Выполните smoke test в тестовой среде, если изменения затрагивают сервер, worker, базу данных либо интеграции.
4. Сливайте PR только после проверки; при необходимости используйте revert отдельным Pull Request.

## Защита main

Рекомендуется включить branch protection для `main`: требовать Pull Request перед merge, ограничить прямые push и включить обязательные status checks. Это предотвращает случайное попадание непроверенных обновлений upstream или рабочих изменений прямо в основную ветку.
