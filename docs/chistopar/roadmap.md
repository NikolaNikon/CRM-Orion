# План адаптации CRM-Orion под ядро «Чистопара»

**Статус:** план первого этапа разработки.  
**Граница этапа:** CRM-ядро банного комплекса и «шахматка» бронирований. Уведомления Telegram/MAX, Bitrix24, iiko, платежи и мобильное приложение в этот этап не входят.

## 1. Цель первого этапа

Нужно превратить существующий CRM-Orion в основу кабинета банного комплекса. Сотрудник комплекса должен суметь создать и поддерживать публичную карточку, добавить разряды и залы, задать цены «от», вести гостей и заявки, а также видеть занятость залов на календарной доске. Карточка банного комплекса должна покрывать реальные данные действующего каталога «Чистопар»: фотографии, контакты, адрес, режим работы, разряды, залы, тарифы, услуги, FAQ, акции и характеристики.[1]

Технически это следует делать как отдельное приложение `chistopar` в монорепозитории Twenty, а не посредством раннего изменения системных сущностей CRM. Twenty уже поддерживает декларативные приложения, объекты, поля, представления, роли, пункты навигации и frontend-компоненты; пример `rich-app` демонстрирует именно этот путь.[2] [3] Такой подход снижает будущую стоимость синхронизации с upstream.

| Входит в первый этап | Не входит в первый этап |
|---|---|
| Карточка комплекса и загрузка фотографий | Telegram-бот, MAX-бот и любые внешние уведомления |
| Разряды, залы, тарифы, услуги, блокировки времени | Bitrix24, iiko и другие интеграции |
| Гости, ручные заявки и статусы бронирования | Онлайн-оплата, предоплата и возвраты |
| «Шахматка» занятости и проверка пересечений | Мобильный клиент iOS/Android |
| Публичный API как контракт следующего шага | Публикация публичного виджета бронирования на сайте |

## 2. Целевая граница в репозитории

Новый предметный код изолируется в `packages/twenty-apps/internal/chistopar/`. Пакет строится на `twenty-sdk` и `twenty-client-sdk`, как внутренние и примерные приложения в текущем репозитории. В нём будут находиться конфигурация приложения, описания объектов, полей, представлений, навигации, ролей и custom frontend-компонентов.[2] [4]

```text
packages/twenty-apps/internal/chistopar/
├── application.config.ts               # Метаданные приложения и настройки
├── src/objects/                        # Комплекс, разряд, зал, тариф, услуга, гость, заявка
├── src/fields/                         # Дополнительные поля и связи
├── src/views/                          # Карточки, списки, фильтры, Kanban/табличные представления
├── src/navigation-menu-items/          # Разделы интерфейса «Чистопара»
├── src/page-layout-tabs/               # Вкладки карточки комплекса и зала
├── src/components/                     # «Шахматка» и вспомогательные UI-компоненты
├── src/logic-functions/                # Проверка пересечений и правила статусов
└── src/roles/                          # Права владельца, управляющего и администратора
```

На первом шаге основной сервер `twenty-server` не изменяется. Изменения в серверном ядре допускаются только если после проверки SDK подтвердится, что для атомарной проверки временных пересечений либо ограниченного публичного API недостаточно возможностей приложения. Это решение принимается после прототипа заявок, а не заранее.

## 3. Предметная модель

| Объект | Основные поля | Ключевые связи и правила |
|---|---|---|
| Банный комплекс | Название, slug, описание, адрес, контакты, режим работы, фотографии, статус публикации | Содержит разряды, сотрудников и общие настройки. Поле фотографий реализуется как `FILES`; такой тип поддерживается SDK.[5] |
| Разряд | Название, описание, фото, активность, порядок показа | Принадлежит комплексу и объединяет залы. Сам по себе не является минимальной единицей бронирования. |
| Зал | Название, тип, вместимость, цена «от», минимальная длительность, шаг слота, фото, активность | Принадлежит разряду; это единственная сущность, по которой строится доступность и «шахматка». |
| Тариф | Название, цена «от», дни недели, время начала/окончания, комментарий, активность | Привязывается к залу или разряду. В первом релизе отображает условия, но не считает финальную сумму. |
| Услуга | Категория, название, длительность, цена, описание, активность | Принадлежит комплексу; позднее может быть добавлена в заказ. |
| Гость | Имя, телефон, email, комментарий, источник | Имеет историю заявок и бронирований. |
| Заявка/бронирование | Зал, гость, начало, окончание, число гостей, цена «от», статус, источник, комментарий сотрудника | Проверяется на временное пересечение перед сохранением; получает неизменяемую историю статусов. |
| Блокировка времени | Зал, начало, окончание, причина, автор | Закрывает временной интервал для ремонта, уборки или ручного резерва. |

Статусы заявки первого этапа: `НОВОЕ`, `НА_ПОДТВЕРЖДЕНИИ`, `ПОДТВЕРЖДЕНО`, `ОТКЛОНЕНО`, `ОТМЕНЕНО`, `ЗАВЕРШЕНО`, `НЕЯВКА`. В занятость «шахматки» входят как минимум `НА_ПОДТВЕРЖДЕНИИ`, `ПОДТВЕРЖДЕНО` и блокировки; точное правило по статусу `НОВОЕ` определяется на этапе публичного бронирования.

## 4. Модули пользовательского интерфейса

| Раздел меню | Пользовательская ценность | Первый набор функций |
|---|---|---|
| Карточка комплекса | Комплекс сам поддерживает информацию в каталоге | Редактирование текста, контактов, адреса, режима работы, фото и статуса заполненности. |
| Разряды и залы | Структура того, что предлагает комплекс | Создание разрядов, вложенных залов, вместимости, цены «от», фото и параметров доступности. |
| Тарифы и услуги | Витрина коммерческих условий | Условия тарифов по дням/времени; услуги по категориям и длительности. |
| Гости | История взаимодействия с посетителем | Поиск гостя, карточка контакта, история заявок. |
| Заявки | Операционная работа администратора | Создание вручную, изменение статуса, редактирование данных, фильтрация по датам и залам. |
| «Шахматка» | Быстрый контроль доступности | Дневная сетка: строки — залы, колонки — временные слоты, визуальные карточки заявок и блокировок. |

Для первого технического прототипа «шахматка» должна быть **дневной**, с конфигурируемым шагом по умолчанию 30 минут. Её минимальные действия: открыть заявку, создать ручную заявку, добавить блокировку, сменить зал через редактирование и отфильтровать по разряду. Перетаскивание, недельный режим, массовая печать и аналитика не включаются до проверки базового процесса администратора.

## 5. Последовательность разработки

| Очередь | Изменения в репозитории | Результат и критерий готовности |
|---|---|---|
| 0. Подготовка среды | Зафиксировать Node.js 24.5+, Yarn 4, локальные PostgreSQL/Redis; поднять CRM и проверить установку примера приложения | Разработчик локально устанавливает приложение в workspace через `yarn twenty remote:add` и `yarn twenty dev`.[4] |
| 1. Каркас приложения | Создать пакет `packages/twenty-apps/internal/chistopar`, `application.config.ts`, роли и базовую навигацию | Приложение отображается в `/settings/applications` и устанавливается в тестовый workspace. |
| 2. Справочники комплекса | Добавить объекты комплекса, разряда, зала, тарифа и услуги; связи, фото, формы и представления | Пользователь создаёт комплекс, несколько разрядов и залов, заполняет цены «от» и видит их в карточках. |
| 3. Гости и заявки | Добавить гостя, заявку, блокировку, статусы, временные поля и базовую историю изменений | Администратор вручную создаёт и подтверждает заявку на зал; пересекающаяся бронь корректно отклоняется. |
| 4. Правила доступности | Реализовать серверно надёжную проверку пересечения интервалов, правила рабочего времени и минимальной длительности | Нельзя создать две занятые записи на один зал и пересекающееся время даже при параллельных запросах. |
| 5. «Шахматка» | Создать custom frontend-компонент, дневную сетку, фильтры, отображение статусов и блокировок | Администратор за один экран видит занятость всех залов и открывает нужную заявку. |
| 6. Тесты и приёмка | Модульные тесты правил времени, интеграционные тесты установки приложения, smoke-test сценариев CRM | Проверены ключевые сценарии: карточка, фото, зал, гость, заявка, блокировка и отсутствие пересечений. |
| 7. Подготовка внешнего контракта | Описать публичную модель доступности и заявки, но не включать UI/интеграцию | Готов технический контракт для следующего этапа: сайт/виджет создаёт заявку через ограниченный API. |

## 6. Критические технические правила

Проверка временных пересечений должна выполняться на сервере, а не только в интерфейсе. Клиентская «шахматка» может показывать свободный слот, но единственным источником истинности остаётся серверная транзакция. При конкурирующих запросах сервер обязан выбрать только одну запись или выдать понятную ошибку о занятости.

Фотографии и документы должны храниться через встроенную файловую модель CRM, а не через URL, введённые пользователем. Доступ к редактированию комплекса ограничивается ролями «владелец» и «управляющий», тогда как «администратор» получает операционные права на заявки и календарь без возможности менять критические данные профиля.

На этом этапе уведомления и внешние интеграции не реализуются. Для них в модели оставляются события `booking.created`, `booking.statusChanged` и технические идентификаторы интеграций, однако фоновые worker-процессы, токены ботов и webhooks не добавляются.

## 7. Проверка качества и способ внесения изменений

Каждая очередь выполняется в отдельной локальной ветке. Перед объединением требуются форматирование, lint, typecheck, сборка приложения и соответствующие интеграционные тесты. Изменения в GitHub и коммиты будут выполняться только после отдельного подтверждения пользователя; на текущем шаге документ описывает работу без внесения кода в репозиторий.

| Вид проверки | Применение |
|---|---|
| Установка приложения | Проверяет, что метаданные, объектные декларации и роли корректно принимаются workspace. |
| Unit-тесты | Проверяют статусные переходы, расчёт временных интервалов и определение пересечений. |
| Integration-тесты | Проверяют создание связанного набора «комплекс → разряд → зал → заявка». |
| UI smoke-test | Проверяет карточку комплекса, форму заявки и дневную «шахматку» в браузере. |
| Приёмка на сценарии | Администратор создаёт и подтверждает бронирование, видит его в доске и не может занять один зал дважды. |

## 8. Следующий этап после CRM-ядра

После завершения и приёмки этапа подключается публичный путь онлайн-бронирования с сайта «Чистопар»: выбор разряда, зала, даты, свободного времени, контактов и создание заявки. Только после стабилизации этого маршрута добавляются Telegram/MAX, поскольку они должны потреблять уже устойчивое событие создания заявки, а не компенсировать пробелы в модели данных.

## Подтверждение для начала разработки

План предполагает, что первый интерфейс «шахматки» — дневной, шаг по умолчанию 30 минут, а пользователь видит цену «от» без финального расчёта. После подтверждения можно начинать очередь 0 и создавать отдельное приложение `chistopar` локально, без коммита и push в GitHub.
